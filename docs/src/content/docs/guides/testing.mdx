A game is a plain value and its rules are pure, so you test it without a UI:
start a state, apply inputs, check the result. The testing entry point,
`@drock07/board-game-toolkit-engine/testing`, adds helpers for the rest. The
examples use [Vitest](https://vitest.dev), but nothing depends on it.

| Helper                         | What it does                                                    |
| ------------------------------ | --------------------------------------------------------------- |
| `applyOrThrow(game, s, input)` | Applies an input that must be legal, and returns the new state. |
| `simulate(game, opts)`         | Plays a list of inputs from `init`, and returns every state.    |
| `playBots(game, opts)`         | Plays a game with bots, and returns every state and input.      |
| `record(game, opts, choose)`   | Plays a game and records it as a golden replay.                 |
| `hashState(state)`             | A short, stable hash of a state.                                |
| `fuzz(game, opts)`             | Plays many random games, checking every step.                   |

## Test a rule

Get the game into a situation, apply an input, and check what changed. Each
rule is tested through the inputs that reach it, the same way a player
reaches it. `applyOrThrow` applies an input and throws with the reason if it
was rejected, so a test fails at the input that went wrong:

<Source
  file="games/crazy-eights/crazy-eights.test.ts"

/>

For a rejected input, use `apply` and check its `{ ok: false, reason }`:
`expect(apply(game, s, input)).toEqual({ ok: false, reason: "…" })`.

## Get to a situation

Scripting dozens of inputs to reach one position is brittle. Two ways around
it:

- **Search seeds.** The opening is a function of the seed, so try seeds until
  one deals what you need, as Crazy Eights' tests do below.
- **Arrange the state.** A state is JSON, so a test can copy one and move
  entities by hand, like giving one player's cards to another. Keep fixtures
  like this to tests; they skip the rules that would have made the move.

## Golden replays

A golden replay is a recorded game, committed to the repo: the players, the
seed, the inputs, and a hash of the final state. A game is a function of its
seed and inputs, so if a change alters behavior anywhere along the way, the
replay reaches a different hash and the test fails.

`record` plays a game, asking your function for each input, and returns the
recording. `replayInputs` plays it back:

<Source file="snippets/testing.test.ts" region="record" title={false} />

`hashState` hashes a state's JSON with sorted keys, so equal states always
hash the same. An input that no longer replays makes `replayInputs` throw a
`SaveError` naming it.

Every example keeps a `golden.json` and checks it in its tests. They record
with `playBots`, which returns the same inputs `record` would, and use
Vitest's `toMatchFileSnapshot` to write the file the first time:

<Source
  file="games/tic-tac-toe/tic-tac-toe.test.ts"
  region="golden"
  title={false}
/>

When a change in behavior is intended, the hash changes. Check that the new
game is right, then update the snapshot (`vitest -u`) to record it.

## Fuzzing

`fuzz` plays random games: for each seed it starts a game and has a seeded
`randomBot` pick among the legal inputs until the game ends or `maxInputs`
runs out.

<Source file="snippets/quickstart.test.ts" region="fuzz" title={false} />

After **every input** it checks that:

- someone has a legal input while the game is running. A running game where
  nobody can act is stuck;
- every legal input it's offered passes `check`, and the one it picks
  applies;
- the events replay onto the old state to give the new one, and each
  player's share of them replays onto their old view to give their new view;
- no player's view or events carry a hidden entity's id or props, or an
  effect whispered to someone else;
- the state is plain JSON.

It also checks the opening state's views. An error thrown along the way, from
rules code or the engine, is a failure too. Each failure has the seed, the
step and the message. The seeds are `fuzz-0`, `fuzz-1` and so on, and
`seeds` also takes a list, so `fuzz(game, { seeds: ["fuzz-17"], … })` plays
that exact game again while you debug it.

`fuzz` returns `{ runs, finished, inputs, failures }`. `finished` counts the
games that ended within `maxInputs`; for a game that loops forever, like the
examples' "play again" games, it stays at zero, and that's fine.

## Fuzzing in CI

The examples share one fuzz test helper. Each game's `fuzz.test.ts` is three
lines, and the helper fuzzes 100 seeds locally and 1,000 in CI:

<Source file="games/fuzzCase.ts" />

<Source file="games/crazy-eights/fuzz.test.ts" />

- **Seeds in batches.** One long synchronous run starves Vitest's worker on a
  slow runner, so the helper fuzzes 50 seeds at a time and yields between
  batches.
- **A file per game**, so games fuzz in parallel.
- **`FUZZ_SEEDS`** overrides the count, to fuzz harder before a release.
