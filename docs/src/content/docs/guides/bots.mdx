A bot plays a seat. It's a function the host calls whenever that seat may
act, `(legal, { view, player, random }) => input`: it gets the seat's legal
inputs and what the seat may see, and returns one of the inputs.

- **`legal`** is the seat's [legal inputs](/board-game-toolkit/concepts/model/)
  right now, typed by the game's actions. Return one of them.
- **`view`** is the seat's [view](/board-game-toolkit/concepts/views/). A bot
  can't see other hands any more than a person can.
- **`player`** is the seat it's playing.
- **`random`** is a seeded generator for the bot's own choices, apart from
  the game's. Use it for tie-breaks, so games with bots replay.

The React host's `Bot` type may return a promise, for a bot that thinks in a
Web Worker or asks a server. The testing entry point's `SyncBot` is the same
shape without the promise, so tests can play whole games synchronously. A
`SyncBot` works as a host bot too; the examples write theirs that way.

## The simplest bot

`randomBot(seed)` picks uniformly among the legal inputs, from its own seeded
generator. It's a fine first opponent, and what `fuzz` plays with.

## A bot of your own

Most bots look at a few kinds of input and prefer some. Roll Five's greedy
bot scores the best category for its dice, rolling again first if that's
worth less than 20:

<Source file="snippets/bots.ts" region="greedy" />

- **Filter `legal` with the action handles.** `score.is` narrows an input to
  that action, so `i.args.category` is typed.
- **Read the view, not the state.** The dice are in `view.vars`, and the
  turn's roll count in what the turn shows, `turnNode.shown(view)`.
- **One bot answers every prompt.** The first answer of a turn must be a
  roll, and between games the only input is "Play again", so the bot falls
  back on whatever is legal.

## Seat a bot

Give a seat a `controller` in `useGame`:

<Source file="games/sealed-bids/SealedBids.tsx" region="host" />

- A bare id, like `"p1"`, is a human seat. Its legal inputs are in `g.legal`
  when it's the viewer.
- **`botDelay`** is how long a bot waits before answering, in milliseconds,
  so people can follow. It defaults to 500.

The host asks a bot when its seat may act, has something legal to do, and
event playback has finished. It hands the bot that seat's view of the
committed state, and drops the answer if the game moved on while the bot was
thinking. The engine checks a bot's input like anyone else's; if it's
rejected, the host logs why.

Bots' `random` is seeded from the game's seed, so a game with a fixed seed
plays out the same way each time.

## Bots in tests

`playBots` from the testing entry point plays a game with bots, without a
host:

<Source file="snippets/bots.test.ts" region="playBots" title={false} />

Pass one bot for every seat, or a bot per seat by id, for example
`{ p1: minimaxBot, p2: randomBot("x") }`. It stops when the game ends, when
no bot seat can act, or after `maxInputs`. It returns every state, starting
with `init`'s, and the inputs, ready to record as a
[golden replay](/board-game-toolkit/guides/testing/). Every input is checked
as `apply` would, and a rejected one throws.

Testing a bot is testing a claim about it. Tic-Tac-Toe's tests play minimax
against itself and against `randomBot` for 20 seeds, and check that it always
ties itself and never loses to random play.

## Legal inputs come from enumerate

A bot can only play what `legalInputs` offers, and an action with args offers
what its `enumerate` lists. If a bot never plays some move, check that
`enumerate` lists it. `enumerate` may list less than `validate` accepts:
Blackjack's bets enumerate chip amounts and all-in, so bots bet those, while
its `validate` accepts any whole amount up to the bankroll.
