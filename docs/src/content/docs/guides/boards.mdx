Many games have several copies of one kind of place: Azul's factories and
each player's five pattern lines, Splendor's three card rows, a chessboard's
64 squares. A zone declared with `perPlayer` or `count` is a **zone family**:
one instance per player, per index, or both, all holding the same entity
type with the same visibility.

## Declare a family

This sample drafts tiles, Azul style: a hidden bag, a row of factories sized
by the player count, and five pattern lines per player.

<Source file="snippets/boards.ts" region="zones" />

| Declared                    | Instances                                  | Handle              |
| --------------------------- | ------------------------------------------ | ------------------- |
| neither                     | `bag`                                      | `bag` itself        |
| `perPlayer: true`           | `hand:ann`, `hand:bob`, …                  | `hand.of("ann")`    |
| `count: n`                  | `factory:0` … `factory:n-1`                | `factory.at(2)`     |
| `perPlayer: true, count: n` | `line:ann:0` … `line:ann:4`, for each seat | `line.of("ann", 3)` |

`count` is a number, or a function of the player count, as the factories'
is. The engine creates every instance at `init`, before `setup`, so the set
of zones is fixed for the whole game.

Use the handles rather than building id strings. `factory.at(2)` is typed as
a zone that holds tiles, so `tx.moveTop(bag, factory.at(2), 4)` is checked,
and a typo is a compile error instead of an unknown zone at runtime.

## Piles: top visibility and the bottom

Two zone features fit piles and decks:

- **`visibility: "top"`**: everyone sees the top entity, and the rest are
  hidden. A discard pile, or a row where only the next card shows. The
  engine turns the top entity face up and the rest face down as the pile
  changes, so you never flip them yourself.
- **`at: "bottom"`**: `tx.move` and `tx.moveTop` put entities on top by
  default; `{ at: "bottom" }` puts them under, keeping their order. Use it to
  tuck a card under a deck, or to deal a hand in order: Blackjack deals each
  card to the bottom of a hand, so the hand reads in the order it was dealt.

The demo puts both together: a shared `"top"` pool, and three piles per
player. Take moves the pool's top token to one of your piles; shift moves a
pile's top token to the bottom of the next pile.

## Grids and graphs

A grid is a counted family: `zone("cell", { holds: piece, count: 64 })` for
a chessboard, with `cell.at(row * 8 + col)` for a square. Write the
coordinate maths and the adjacency as plain functions next to your rules:
which cells are neighbors, whether diagonals count, where the walls are.
Square or hex, a map's named cities and its routes are rules of your game,
and a function says them more clearly than a topology format would.

A board whose spaces have names, like the cities on a map, can declare one
zone per space and keep its edges in a constant.

## When to keep a board in vars

A family pays off when pieces **move** between spaces, need
**per-space visibility**, or should produce `moved` events a UI can animate.
When a board is only marks or values, a var is simpler:

- [Tic-Tac-Toe](/board-game-toolkit/examples/tic-tac-toe/) keeps its nine
  cells in `vars.marks`. Marks never move or hide, and the win check wants a
  flat array.
- [Dungeon Crawl](/board-game-toolkit/examples/dungeon-crawl/) keeps its
  rooms in `vars.grid`. Each room is a record (a monster, treasure, whether
  it's been explored), not a place pieces move through.

The rule of thumb from [State](/board-game-toolkit/concepts/state/): if it
moves or hides, it's an entity in a zone; otherwise it's a var.
