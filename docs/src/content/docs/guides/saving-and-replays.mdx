A game is fully determined by its players, its seed and its inputs, and its
state is plain JSON. So there are two ways to keep one: store the state, or
store the inputs and replay them. This page shows both, and the undo and
replay viewers they make easy. The samples use High Card from the
[concept pages](/board-game-toolkit/concepts/model/).

## Save the state

<Source file="snippets/savingAndReplays.test.ts" region="save" title={false} />

- **`save(game, state)`** writes the state as a JSON document, stamped with
  the game's **spec hash**.
- **`load(game, text)`** reads it back. It throws a `SaveError` if the text
  isn't a save, is from a newer save format, or was written by a game whose
  spec hash differs.
- **`specHash(game)`** is a hash of the game's spec: its zones, its flow's
  nodes and their settings, its abilities and effects. A state's frames name
  flow nodes by id, so a state only makes sense in a flow with the same
  nodes. The hash makes a mismatch fail clearly at `load`, instead of deep
  in the flow later.

The hash doesn't cover rules code. Change what an action's `execute` does,
or a step's body, and old saves still load and play on under the new rules.
Add a node or a zone, and they don't.

A save works at any point: mid-turn, in the middle of a reaction, with
[several fibers](/board-game-toolkit/guides/simultaneous-turns/) running.
The flow's position is part of the state.

## Save the inputs

The players, the seed and the accepted inputs are a complete record of a
game, and a small one. `replayInputs` plays them from the start:

<Source file="snippets/savingAndReplays.test.ts" region="log" title={false} />

- Every input must still be legal. The first that isn't throws a
  `SaveError` naming its index, player, action and why it was rejected.
- A log survives rules fixes that don't change what its inputs did, even
  ones that change the spec hash. A save doesn't.
- A log is history. You can show it as a game log, replay it for review, or
  rebuild any point in the game from it.

Which to keep? A save loads instantly and needs nothing else. A log is
smaller, keeps the whole game, and is what you want for bug reports and
[golden replays](/board-game-toolkit/guides/testing/). Many hosts keep both:
the log as the record, and a recent save to start from quickly.

## Undo

<Source file="snippets/savingAndReplays.test.ts" region="undo" title={false} />

- **Keep every state.** `apply` never changes the state it's given, so a
  stack of states is a full history. Undo pops it.
- **Replay all but the last input**, when you only keep the log.

Undo needs care with hidden information. Undoing past a card draw lets a
player see the card and choose differently. Most games allow undo only
until something new is revealed, or only in single-player games.

## Replay viewers

To step through a finished game, apply its inputs one at a time and keep
each result. Each step's events are the same events live play produced, so
the same animations play them back:

Show each player's share with `viewEvents(game, events, player)`, as in
live play. See [Events](/board-game-toolkit/concepts/events/).

## With the React host

`useGame` starts a game from a seed, and `restart(seed?)` starts it over. To
put a logged game back on screen, start from the log's seed and submit its
inputs in order; their events play back like any others. The host's own
`log` is the viewer's events, for showing what happened, not the inputs.
