:::note[A pattern, not a package]
The toolkit has no networking. This page shows how the engine fits an
authoritative server, with a room you can adapt to any transport. The room
is tested, with the test standing in for the clients.
:::

The engine is pure TypeScript with no UI, so it runs on a server unchanged.
The server holds the full state and applies every input. Each client gets
only what its player may see: their view when they join, and their share of
each input's events after that.

## The shape

1. The server creates the game with `init` and keeps the state.
2. A client connects as a player and is sent their view, `view(game, state,
player)`, and their legal inputs.
3. The client sends an input. The server checks it came from that player's
   seat, and applies it with `apply`.
4. If it's rejected, the sender gets the reason. If it's accepted, the
   server sends **every** player their share of the events,
   `viewEvents(game, events, player)`, and their new legal inputs.
5. Each client replays its events onto its view, animating as it goes.

## Messages

<Source file="snippets/server.ts" region="messages" title={false} />

A client never gets the state, only a view and the events it may see. Those
are enough: replaying a player's events onto their old view gives exactly
their new view, `waiting` and `shown` included. `fuzz` checks that on every
input of every game, so a client that stays in sync by replaying is
relying on a tested guarantee. See
[Events](/board-game-toolkit/concepts/events/).

## The room

<Source file="snippets/server.ts" region="room" />

- **`join`** sends the whole view. It's also how a client reconnects: send
  the current view again, and replay from there.
- **`receive`** takes the sender from the connection, never from the
  message. An input whose `player` isn't the sender's seat is refused
  before the engine sees it. The engine then rejects anything illegal, like
  an input out of turn, with a reason the client can show.
- **`play`** sends each player their own share of what happened. A card
  dealt to bob is a `moved` event for ann too; she sees a card go to his
  hand, not which card.
- **Legal inputs come from the server.** Working out what's legal needs the
  full state, which the client doesn't have, so each message carries the
  player's legal inputs. Use them to enable buttons; the server still checks
  every input it receives.
- **Bots run on the server.** A bot is a function from a seat's legal inputs
  to one of them, like the engine's `randomBot(seed)`. After each input the
  room lets bot seats answer until a person must act. See
  [Writing a bot](/board-game-toolkit/guides/bots/).
- **`restore`** rebuilds a room from its log: players, seed and inputs,
  replayed with `replayInputs`. Store the log as the game goes, and a
  restart loses nothing.

## On the client

Clients don't run the rules. A client keeps the view it was sent and folds
each update's events onto it with `replay`:

<Source file="snippets/server.test.ts" region="client" title={false} />

Render from that view, and play the events back one at a time if you
animate. The React host does this for a local game; for a networked one,
render from the view you keep yourself.

## Things to get right

- **Never send the state.** It holds every hand and the random generator's
  state, from which a client could predict every shuffle.
- **Keep the seed secret** until the game is over, for the same reason.
- **Authenticate the seat.** Take the player from the connection, as the
  room does.
- **Keep secrets out of vars.** Vars go to every player. Anything one player
  shouldn't know belongs in a zone they can't see; see
  [Hidden information](/board-game-toolkit/guides/hidden-information/).
