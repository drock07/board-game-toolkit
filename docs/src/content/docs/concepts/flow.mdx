The **flow** is the order things happen in: rounds, turns, choices, and what
comes after them. It's a tree of **nodes**, built with the core's builders,
that the engine runs for you. Your rules code never says "now it's bob's
turn"; the flow does.

## Nodes

Each node kind does one job. The built-ins:

| Node                                                               | What it does                                                       |
| ------------------------------------------------------------------ | ------------------------------------------------------------------ |
| [`seq`](/board-game-toolkit/reference/flow/seq/)                   | Runs its children in order.                                        |
| [`step`](/board-game-toolkit/reference/flow/step/)                 | Runs rules code in one transaction, without waiting.               |
| [`loop`](/board-game-toolkit/reference/flow/loop/)                 | Repeats its body until a condition holds (or forever).             |
| [`branch`](/board-game-toolkit/reference/flow/branch/)             | Runs the first case whose condition holds.                         |
| [`turns`](/board-game-toolkit/reference/flow/turns/)               | Players take turns at its body, in seat order.                     |
| [`prompt`](/board-game-toolkit/reference/flow/prompt/)             | Waits for the current player to take one of its actions.           |
| [`turn`](/board-game-toolkit/reference/flow/turn/)                 | A prompt held open across several answers, with per-action limits. |
| [`everyone`](/board-game-toolkit/reference/flow/everyone/)         | Waits for every player to answer once, in any order.               |
| [`anyone`](/board-game-toolkit/reference/flow/anyone/)             | Waits for the first answer from any of a set of players.           |
| [`simultaneous`](/board-game-toolkit/reference/flow/simultaneous/) | Runs its body for every player at once.                            |
| [`outcomes`](/board-game-toolkit/reference/flow/outcomes/)         | The ways its body may end early.                                   |

You can write your own; see
[Writing a node kind](/board-game-toolkit/guides/node-kinds/).

## How it runs

The engine keeps a stack of **frames**, one per running node, inside the
state. It runs the top frame until it either finishes, starts a child, or
**waits**. Waiting nodes (`prompt`, `turn`, `everyone`, `anyone`) are the only
places the game stops: after an input, the engine runs every node it can
until the flow is waiting again, or the game ends.

In High Card, after `init`:

<Source file="snippets/highCard.ts" region="rules" />

1. The `loop` checks its `until` (not yet) and starts its body.
2. The `seq` starts its first child, the dealing `step`, which runs and ends.
3. `turns` picks the first seat and starts its body, the `prompt`, which
   waits for that player.

So the state `init` returns is already waiting on the first player. When she
plays, the prompt ends, `turns` moves to the next seat, and so on, until the
scoring step, the loop's next check, and eventually the last step, which
calls `tx.end()`.

## Who acts

A waiting node decides who it waits on. A `prompt` waits on the **bound
actor**: the player whose turn it is, set by the nearest `turns` above it (or
the first seat if there's none). `everyone` and `anyone` name their own
players. `actors(game, state)` lists everyone the flow is waiting on, and
`legalInputs(game, state, player)` lists what a player may do: every action
the waiting node offers them, with every enumerated arg that validates.

An input names the player and the action, never a node: `{ player, action,
args }`. The engine finds the waiting node that offers that action to that
player. A stale or out-of-turn input is simply illegal.

## What UIs see of the flow

A view carries what the flow is waiting on, so a UI can say "Waiting for bob:
Play your card":

- **`view.waiting`**: each open prompt's `label` and its `actors`.
- **`view.shown`**: what nodes publish. `turns` publishes whose turn it is and
  the turn and round number; `turn` publishes its per-action counts; `loop`
  its pass number. Read them typed through the node's definition:
  `turnsNode.shown(view)?.round`. Rules code can read them the same way, in a
  `validate`. See [What nodes show](/board-game-toolkit/reference/flow/shown/).

## Several flows at once

`simultaneous(body)` runs its body once for every player at the same time,
each on its own **fiber**: a separate stack bound to that player. Each fiber
waits on its own player, and `simultaneous` ends when all of them have
finished. `everyone(…)` is shorthand for `simultaneous(prompt(…))`. See
[Simultaneous turns](/board-game-toolkit/guides/simultaneous-turns/).

## Ending early

A node can end before its body finishes when something happens: a player
busts, the dragon falls. Wrap the body in `outcomes` and either give an
outcome a condition, checked after every change, or raise it from an action
by returning `{ exit: "name" }`. See
[Outcomes](/board-game-toolkit/concepts/outcomes/).

## Why a tree

The flow lives in the state as frames, which are plain JSON. So a game saved
in the middle of a turn, a reaction or a simultaneous round loads and carries
on exactly. Tools can draw it, like the graph above and the
[devtools](/board-game-toolkit/guides/devtools/). And an outcome or a guard on
an outer node can cancel everything inside it, however deep, without any
rules code knowing it was there.
