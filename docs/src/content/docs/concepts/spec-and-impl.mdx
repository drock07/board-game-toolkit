Every game has two halves:

|                         | Spec                                          | Impl                                                                    |
| ----------------------- | --------------------------------------------- | ----------------------------------------------------------------------- |
| **What**                | The game's structure                          | The game's rules                                                        |
| **Form**                | Plain JSON data                               | TypeScript functions                                                    |
| **Holds**               | Players, zones, vars, the flow tree, triggers | `setup`, conditions, steps, actions, lists, locals, choices, visibility |
| **Refers to the other** | By name: `step("deal", "dealSeven")`          | By key: `steps: { dealSeven(tx) {…} }`                                  |

## The spec is data

A spec is an object that would survive `JSON.stringify`. The builders
(`seq`, `loop`, `decision`, …) are shorthand: each returns a plain object, so
these two are the same node:

```ts
step("deal", "dealSeven");
{ kind: "step", id: "deal", run: "dealSeven" }
```

Because it's data, a spec can be saved to a file and loaded back
([`toJSON` and `fromJSON`](../../reference/spec/json/)), diffed in a code
review, and drawn as a diagram by the devtools' `FlowGraph`. Conditions can
even be written inline as JSON [expressions](../../reference/spec/expressions/)
instead of named functions.

- **`id` and `version`**: saved into every state. `apply` refuses a state
  from a different id or version, so an old save can't run against changed
  rules.
- **`players`**: the allowed player count.
- **`zones`**: named places entities can be. See [State](../state/).
- **`vars`**: the declared top-level vars, with their visibility. See
  [Views](../views/).
- **`flow`**: the root of the flow tree. See [Flow](../flow/).
- **`subflows`** and **`triggers`**: reusable flows and interrupts, both
  optional.

## The impl is named functions

The impl groups functions by what they do. Each kind gets different powers:

| Group        | Called when                                                  | Gets                                                                                      | Returns                                 |
| ------------ | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------- | --------------------------------------- |
| `setup`      | Once, at `init`                                              | A transaction and `{ players, options }`                                                  | Nothing                                 |
| `conditions` | A guard, `until`, `while`, `branch` or trigger is checked    | A read-only `StateReader` and the scope                                                   | `boolean`                               |
| `steps`      | The flow reaches a `step` node                               | A transaction                                                                             | Nothing                                 |
| `actions`    | A player answers a `decision`                                | `validate`: reader, args, scope. `execute`: transaction, args. `enumerate`: reader, scope | `true` or a reason; nothing; legal args |
| `choices`    | A player answers a `choose`                                  | A transaction and the selection                                                           | Nothing                                 |
| `lists`      | An `each` over a ref, `choose` options, or a `{ ref }` actor | A reader and the scope                                                                    | A JSON array                            |
| `locals`     | A node with `locals` is entered                              | A reader and the scope                                                                    | The node's starting locals              |
| `visibility` | A zone's custom visibility is checked                        | A reader, the entity and the viewer                                                       | `boolean`                               |

Only `setup`, steps, action `execute` and choices get a transaction. Everything
else reads state and can't change it, so a condition can be checked as often
as the engine likes.

## defineGame checks the connection

```ts
export const game = defineGame({ spec, impl });
```

`defineGame` compiles the spec and checks it against the impl. It throws a
`GameDefinitionError` that lists every problem at once, such as:

- A name the spec uses that the impl doesn't have:
  `Missing impl.conditions.boardDecided (used by node "turns" until)`.
- An impl entry the spec never uses:
  `Unused impl.steps.oldStep: the spec never references it`.
- Duplicate node ids, unknown subflows, a subflow that uses itself.
- A `loop` that could never end or wait for input.
- `actor: "current"` outside an `each` over players.
- An `exit` node raising an outcome nothing handles.
- A malformed expression, or one naming an undeclared var or unknown zone.

The first two are also **type errors**, so your editor flags them before
anything runs. For that, the spec needs `as const` (to keep names literal) and
the impl needs `satisfies GameImpl<Types>` (to type handlers without widening
their keys):

`TypesFor` reads zone names from the spec and takes the rest from what you
declare: `vars`, entity props by type, and optionally node `locals`. Declaring
something that isn't JSON, like a `Date` or a `Map`, is a type error too.
With the bundle in place, a misspelled zone like `tx.move(id, "dicard")` or
wrong entity props are compile errors as well.

## Why split them?

- **Rules stay small.** Each function does one thing: decide if a hand is
  empty, deal seven cards. The order they run in lives in the spec, where you
  can see it.
- **The structure is inspectable.** Tools can read the flow without running
  it. The [Flow Gallery](../../examples/flow-gallery/) draws every example's
  spec, and the live devtools highlight the running nodes.
- **Mistakes are caught early.** A typo in a name is a compile error, not a
  game that hangs on turn three.
