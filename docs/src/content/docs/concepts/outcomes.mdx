Most nodes end normally: a `seq` runs out of children, a decision gets its
answer. That normal ending is the outcome `"done"`. Board games also need to
stop things early: you bust, so your turn and the dealer's are skipped; the
boss dies mid-fight, so the whole run ends in victory. That's what
**outcomes** are for.

## Guards: `exits`

Any node can declare `exits`: named outcomes, each with a condition.

<Source file="games/tower-battler/spec.ts" title="tower-battler/spec.ts" />

**Guards are checked after every transaction**, not just when the node
starts or ends. So a card that deals the last point of damage ends the
`rounds` loop on the spot, in the middle of the player's turn. Everything
inside the loop is cancelled, and the flow carries on after it.

Guards are checked **outermost first**. If two guards hold at once, the one on
the outer node wins. Dungeon Crawl relies on this: killing the boss also kills
the monster in the room, and the outer `victory` guard wins over the inner
`killed` one.

## Handling an outcome: `on`

A node handles the outcomes named in its `exits` or `on`. When it ends with
one, its `on` flow for that outcome runs (if there is one), and then the node
is done, as if it had ended normally:

<Source file="games/dungeon-crawl/spec.ts" title="dungeon-crawl/spec.ts" />

Here `run` ends with `victory` or `defeat` from its guards, and its `on` map
runs a different flow for each before the game's "Play again" pause.

## Raising an outcome

Rules code can end a node too. `tx.exit(outcome)` raises an outcome when the
transaction commits:

<Source file="games/dungeon-crawl/impl.ts" region="flee" />

A raised outcome **unwinds** the flow: it ends the current node, then its
parent, and so on, until it reaches a node that handles it. Here the combat
`fight` loop handles `fled` with `on: { fled: step("logFlee", "logFlee") }`.
The rest of the handler that called `tx.exit` still runs, and the first
`tx.exit` in a transaction wins.

The `exit` node does the same from the flow itself: `exit("giveUp", "forfeit")`
raises `"forfeit"` when the flow reaches it. `defineGame` checks that some
enclosing node handles it.

If an outcome unwinds all the way to the root without being handled,
`apply` throws `UnhandledOutcomeError`: it's a bug in the game, since the
spec should say where every outcome goes.

## A few rules

- `"done"` is the normal outcome. You can't raise it.
- A node doesn't handle outcomes raised from its own `on` flows; they unwind
  past it.
- Guards aren't checked on a node while its `on` flow is running.
- Cancelled nodes emit `flow` exit events, so a UI or trigger can see them end.
