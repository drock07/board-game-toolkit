A game's state is one plain JSON object. It holds the players, the vars, every
entity and the zones they're in, the seeded random number generator, and the
flow's frames. Because it's JSON, you can save it, send it, diff it and
replay to it. The engine never changes a state in place; `apply` returns a
new one.

## Vars or entities?

There are two places to keep things, and the choice is simple:

- **If it moves or hides, it's an entity in a zone.** Cards, tokens, dice that
  sit somewhere, tiles. Zones say who may see what's in them, so hidden
  information lives here, and so do the events a UI animates ("this card
  moved from the deck to bob's hand").
- **Otherwise, it's a var.** Scores, the round number, a grid of cells, the
  active color in Crazy Eights. Vars are the same for every player.

:::caution[Don't put hidden ids in vars]
Every player can read the vars. If you store the id of a card in a hidden
zone in them, a player can follow that card. Keep references to hidden
entities out of vars, or keep them only once the card is public, as High
Card does with the ranks it records when cards are played.
:::

## Entities and zones

An entity has an `id`, a `type`, its `props` and the `zone` it's in. Zones
list their entities top first. You declare entity types and zones as handles,
and pass the zones to `define`:

<Source file="snippets/highCard.ts" region="box" />

A zone handle names an instance: `deck`, `hand.of("ann")`, `factory.at(2)`.
Reading through a handle is typed: `s.entities(hand.of(p))` returns
`Entity<{ rank: number }>[]`.

## Changing state: transactions

Rules code changes state through a transaction, `tx`: in a `step`, an
action's `execute`, setup, or an effect's `resolve`. Its ops:

| Op                                     | What it does                                                        |
| -------------------------------------- | ------------------------------------------------------------------- |
| `tx.vars`                              | The vars, as a draft: change them in place, or assign a new object. |
| `tx.create(type, props, zone)`         | Creates an entity at the bottom of a zone.                          |
| `tx.move(ids, zone, { at?, faceUp? })` | Moves entities to the top of a zone (or `at: "bottom"`).            |
| `tx.moveTop(from, to, count?, opts?)`  | Moves the top `count` entities from one zone to another.            |
| `tx.shuffle(zone)`                     | Shuffles a zone with the seeded RNG.                                |
| `tx.flip(id, faceUp)`                  | Turns an entity face up or down, whatever its zone's visibility.    |
| `tx.update(entity, patch)`             | Changes some of an entity's props.                                  |
| `tx.destroy(id)`                       | Removes an entity from the game.                                    |
| `tx.random`                            | Seeded randomness: `int`, `float`, `pick`, `shuffle`, `roll(D6)`.   |
| `tx.cause(effect, data)`               | Causes an [effect](/board-game-toolkit/concepts/effects/).          |
| `tx.end(result)`                       | Ends the game.                                                      |

Readers (`s` in conditions, `enumerate` and `validate`) have the same reading
methods, `entities`, `count`, `entity`, `zones`, and the vars, read-only.

Each op is logged as an [event](/board-game-toolkit/concepts/events/). If
rules code throws, `apply` throws too, and the state you passed is untouched.

## Zone families

`perPlayer` and `count` make a zone a **family** of instances, created at
`init`. Here each player has three piles, and a shared pool shows only its
top token:

<Source file="demos/families.ts" region="zones" />

- **`perPlayer: true`**: one per player, `hand.of(p)`.
- **`count: n`**: `n` numbered instances, `factory.at(i)`. `count` may also be
  a function of the player count, `(players) => 2 * players + 1`.
- **Both**: `piles.of(p, i)`.

`s.zones(family, player?)` lists a family's instances in seat order, then
index order. [Boards and zones](/board-game-toolkit/guides/boards/) shows them
at work.

## State that belongs to a moment

Some state only matters while one node runs: how many times you've rolled
this turn, who has answered so far. Nodes keep that in their own frames, so
there's nothing in vars to reset. `turn` counts its answers per action, and
UIs and rules read the counts with `turnNode.shown(view)` or
`turnNode.shown(s)`. See [What nodes show](/board-game-toolkit/reference/flow/shown/).
