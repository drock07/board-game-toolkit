Given the same game, players, seed and inputs, the engine always produces the
same state. That one property gives you a lot:

- **Replays**: store the inputs, rebuild the game.
- **Saves**: store the state, or just the inputs.
- **Undo**: keep earlier states, or replay all but the last input.
- **Bug reports**: a seed and a list of inputs reproduce the bug exactly.
- **Servers**: a server and its clients can run the same rules and agree.
- **Tests**: golden replays catch any change in behavior.

## The seeded RNG

Randomness comes from a generator whose state is part of the game state. In
rules code it's `tx.random`:

| Method           | Returns                                 |
| ---------------- | --------------------------------------- |
| `int(n)`         | A whole number from `0` to `n - 1`.     |
| `float()`        | A number in `[0, 1)`.                   |
| `pick(array)`    | One element.                            |
| `shuffle(array)` | A shuffled copy.                        |
| `roll(die)`      | One of a die's faces, typed by the die. |

`tx.shuffle(zone)` uses the same generator. The engine ships `D4` to `D100`
and `Fudge`; see [Dice](/board-game-toolkit/guides/dice/). The `seed` passed
to `init` is any string. Same seed, same game.

## Replays and saves

<Source file="snippets/highCard.test.ts" region="determinism" title={false} />

- **`replayInputs(game, { players, seed }, inputs)`** plays the inputs from
  the start. An input that doesn't replay throws a `SaveError` naming it,
  which usually means the log is from a different version of the game.
- **`save(game, state)`** writes the state as JSON, stamped with the game's
  **spec hash**: a hash of its zones and flow. **`load(game, text)`** reads it
  back, and refuses a save from a game whose spec hash differs, so a save
  never loads into a flow it doesn't fit.

A save works anywhere: mid-turn, in the middle of a reaction, with several
fibers running. The flow's position is part of the state.

The spec hash doesn't cover rules code. If you change what an action does
but not the flow, old saves still load, and play on under the new rules.

## The spec

`rules` derives a JSON **spec** from your definition: the zones, the flow's
nodes and their settings, the abilities and effects, with names in place of
functions. `game.spec` is it; `toJSON(spec)` and `fromJSON(text)` write and
read it, for tools that draw or diff a game. A spec can't run on its own,
because the rules code it names lives in your module.

## Keeping it deterministic

The engine does its part. Yours is:

- **Use `tx.random`**, never `Math.random`, for anything random.
- **Don't read the clock** or anything else outside the state in rules code.
  The repo's ESLint config bans `Date` in game code for this reason.
- **Keep vars and props JSON**: no `Date`, `Map`, class instances or
  `undefined` in arrays. `fuzz` fails if a state isn't plain JSON.
- **Keep rules code pure**: no side effects outside `tx`, no async.
