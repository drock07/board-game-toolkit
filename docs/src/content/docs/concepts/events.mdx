Every change the engine makes is an **event**. `apply` returns them with the
new state, in the order they happened. UIs animate them, logs show them, and
each player gets only the ones they may see.

## The events

| Event       | When                                                                                                                             |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `created`   | `tx.create`: carries the new entity.                                                                                             |
| `moved`     | `tx.move`, `tx.moveTop`: the entities, each one's old zone (`from`), the new zone (`to`), and `at: "bottom"` if they went under. |
| `shuffled`  | `tx.shuffle`: the zone's entities in their new order, with new refs.                                                             |
| `flipped`   | `tx.flip`, or a `"top"` zone turning its cards: the entity.                                                                      |
| `updated`   | `tx.update`: the entity with its new props.                                                                                      |
| `destroyed` | `tx.destroy`: the entity as it was.                                                                                              |
| `vars`      | A transaction changed the vars: the new vars.                                                                                    |
| `effect`    | `tx.cause`: the effect's `name` and `data`. See [Effects](/board-game-toolkit/concepts/effects/).                                |
| `flow`      | What the flow waits on, or what nodes show, changed: `waiting` and `shown`.                                                      |
| `ended`     | `tx.end`: the result.                                                                                                            |

An event that touches an entity carries the entity **as it is afterwards**.
That one choice is what makes the rest simple: replaying is a fold, and
filtering per player is the same visibility check views use.

## Each player's share

`viewEvents(game, events, player)` is what one player may see of them:

- An entity they can't see becomes a placeholder, `{ ref, zone, hidden }`. A
  card dealt to someone else is still a `moved` event (they see a card go to
  that hand), just not which card.
- An `updated` to an entity they can't see is dropped.
- An `effect` whispered to other players (its `to`) is dropped.
- A `flow` event carries their own `shown`: the root flow's, and their own
  fibers', never another player's.

## Replaying

`replay(view, events)` folds a player's events onto their old view, and gives
exactly their new view. The same works on a whole state with the unfiltered
events. That's how a host animates: it plays a player's events back one at a
time, so the screen moves through every step, and when playback ends it's at
the committed state.

`fuzz` checks this on every input of every game: the events replay to the new
state, and each player's share replays to their new view. A missing event
fails it.

## Events in a UI

With React, `useGameEvent(g, "moved", handler)` runs the handler as each
`moved` event plays back, and waits for a promise it returns, so an
animation can finish before the next event. `useGameEffect(g, effect,
handler)` does the same for one effect, with its data typed. See
[Animating events](/board-game-toolkit/guides/animating-events/).
