These pages are the reference for the flow's nodes: what each one does, its
options, and a live demo you can play. For how the engine runs a flow, read
[Flow](/board-game-toolkit/concepts/flow/) first.

## The built-in nodes

The builders come from your core, once you add them with
`withNodes(defaultNodes)`:

<Source file="snippets/highCard.ts" region="core" />

| Node                                                                          | What it does                                      | Waits on                               | Shows                     |
| ----------------------------------------------------------------------------- | ------------------------------------------------- | -------------------------------------- | ------------------------- |
| [`seq(...children)`](/board-game-toolkit/reference/flow/seq/)                 | Runs its children in order.                       | Nothing                                | Nothing                   |
| [`step(run)`](/board-game-toolkit/reference/flow/step/)                       | Runs rules code in one transaction.               | Nothing                                | Nothing                   |
| [`loop(opts, body)`](/board-game-toolkit/reference/flow/loop/)                | Repeats its body until `until` holds, or forever. | Nothing                                | `{ pass }`                |
| [`branch(cases, otherwise?)`](/board-game-toolkit/reference/flow/branch/)     | Runs the first case whose `when` holds.           | Nothing                                | Nothing                   |
| [`turns(opts, body)`](/board-game-toolkit/reference/flow/turns/)              | Players take turns at its body, in seat order.    | Nothing; binds whose turn it is        | `{ player, turn, round }` |
| [`prompt(opts?, ...actions)`](/board-game-toolkit/reference/flow/prompt/)     | Waits for one answer.                             | The bound player                       | Nothing                   |
| [`turn(opts, ...actions)`](/board-game-toolkit/reference/flow/turn/)          | A prompt held open across several answers.        | The bound player                       | `{ answers, counts }`     |
| [`everyone(opts?, ...actions)`](/board-game-toolkit/reference/flow/everyone/) | One answer from every player, in any order.       | Every player, each on their own fiber  | Nothing                   |
| [`anyone(opts, ...actions)`](/board-game-toolkit/reference/flow/anyone/)      | The first answer from any of a set of players.    | Everyone in `who`, or every player     | Nothing                   |
| [`simultaneous(body)`](/board-game-toolkit/reference/flow/simultaneous/)      | Runs its body for every player at once.           | Whatever its body waits on, per player | Nothing                   |
| [`outcomes(outcomes, body)`](/board-game-toolkit/reference/flow/outcomes/)    | The ways its body may end early.                  | Nothing                                | Nothing                   |

Effects and abilities run as nodes too, pushed by the engine when an effect
is caused or an ability fires; see
[Effects and abilities](/board-game-toolkit/reference/flow/effects/). What
the "Shows" column means, and how a UI reads it, is on
[What nodes show](/board-game-toolkit/reference/flow/shown/).

Only `prompt`, `turn`, `everyone` (through its prompts) and `anyone` wait
for input. Every other node runs straight through, so the game only stops
where one of those is open.

## Conditions and queries are functions of state

Options like `until`, `when`, `from`, `among` and `who` are functions of a
read-only `Reader`: `(s) => s.vars.round === 3`. They see the vars, the
zones, `s.players`, `s.actor` (who the flow is bound to there) and
`s.shown`. They must not change anything, and they run whenever the engine
needs the answer, so keep them cheap.

## How builders become a spec

A builder doesn't run anything. It returns an authored node, and `rules`
**lowers** the whole tree into two parts:

- a **spec**: plain JSON, with a `kind` and an `id` per node, that the
  engine runs, [devtools](/board-game-toolkit/guides/devtools/) draw, and
  saves are checked against;
- an **impl**: your functions, filed by name: steps, conditions, queries
  and actions.

Each node's id is its kind, numbered when repeated (`step`, `step2`, …), and
its functions are filed under names built from the id (`turns.until`,
`branch.when0`, `outcomes.won`). The [seq demo](/board-game-toolkit/reference/flow/seq/)
lowers to:

You rarely need the spec yourself, but it's why a game's state is plain
JSON: frames name nodes by id, so a save holds no functions. A save only
loads into a game with the same spec, so adding, removing or reordering
nodes makes old saves refuse to load; changing what a step or an action
does doesn't. See
[Saving and replays](/board-game-toolkit/guides/saving-and-replays/).

## Errors the flow throws

All of these are bugs in a game, never a player's mistake:

- **`FlowStuckError`**: the flow ran 10,000 nodes without waiting for
  input, usually a `loop` whose body never waits. Its `trace` lists the
  last nodes run.
- **`FlowEndedWithoutEndError`**: the flow ran out without `tx.end()`. End
  the game in a last `step`, or loop forever.
- **`UnhandledOutcomeError`**: an outcome was raised that no enclosing
  `outcomes` lists.
- **`RulesError`**: rules code used the engine wrongly, e.g. `turns` got an
  unknown player from `from`.
